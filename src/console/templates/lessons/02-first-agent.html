1. A model only writes text

A language model takes text in and gives text out. It can't run code, read a file or check a fact by itself. To let it act, you describe tools it may ask for: a name, what it does, and the arguments it takes (as a JSON schema). The model never runs anything; it asks, and your program decides.

2. The agent loop

An agent is a loop around the model:

  you ── task ──► model
                    │  stop_reason = "tool_use":  run_python(code="print(fib(30))")
                    ▼
            your program runs the code (in the sandbox) ── output "832040"
                    │  sent back as a tool_result
                    ▼
                  model ── stop_reason = "end_turn":  "The 30th Fibonacci number is 832040."

Each turn, the API response has a stop_reason. "tool_use" means "I want to call a tool: run it and tell me the result". "end_turn" means "I'm done". Everything an AI coding assistant does (edit files, run tests, search) is this loop with more tools.

3. The conversation is the memory

The API doesn't remember anything between calls. Your program keeps a messages list and sends all of it every time. After two turns it looks like this:

  user:       "What is the 30th Fibonacci number?"
  assistant:  [tool_use  id=tu_1  run_python(code=...)]
  user:       [tool_result  tool_use_id=tu_1  "832040"]
  assistant:  "The 30th Fibonacci number is 832040."

The tool_use_id links each result to the request it answers.

4. Why the tool runs in a sandbox

The code the model writes is untrusted: it can be wrong (an endless loop, deleting the wrong folder) or, if the model was fed malicious text, hostile. Here it runs inside this workspace, with a 20-second timeout and an internet allowlist, and your API key sits in a secret that's masked if anything prints it. The worst it can do is break a disposable workspace.
