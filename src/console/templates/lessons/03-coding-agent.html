1. From one tool to a toolbox

Lesson 2 had one tool. A coding agent needs a few: read a file, write a file, run the tests. You don't script the order; the model decides which tool to call next from what it has seen so far. That's why the tool descriptions matter: they're how the model knows what each one is for.

  run_tests  ──► "2 failures: median, variance"
  read_file  ──► stats.py
  write_file ──► stats.py  (fixed)
  run_tests  ──► "OK"        ──► done: summarise the fix

2. Tests are the goal

"Fix the bugs" is vague; "make these tests pass" is checkable. The agent can verify its own work by running the tests, and you can verify it the same way. Good agents work towards something they can check; that's also why the prompt says to fix the code, not the tests.

3. Guardrails live in the tools

The model chooses the arguments, so every tool treats them as untrusted input:

  • Paths stay inside project/. A request for ../../etc/passwd is refused. The sandbox already protects your machine; this protects the rest of the workspace (like the agent's own code).
  • Output is capped, so a huge test log can't flood the conversation.
  • Errors go back to the model as a tool_result with is_error, instead of crashing the program. The model reads the error and tries something else.

4. Several tool calls at once

One reply can ask for more than one tool (read two files, say). Run them all and send all the results back in a single message, each with its own tool_use_id.
