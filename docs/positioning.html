agent-sandbox · positioning and demo guide · October 2026

Every serious agent now runs in a sandbox. Here's one you own.

agent-sandbox is a self-hosted execution layer for AI agents. An agent sends code over an API, the code runs in a throwaway gVisor container with no network and hard limits, and the result comes back. It runs in your own AWS account, with any model.

These sandboxes are built for the labs' own agents. Muse's VM runs Muse; Dots' computers run Dots. A company building its own agent — on its own data, with the model it chooses, under its own compliance rules — still needs that same layer. That is the gap agent-sandbox fills.
What's built

Four parts, all working on a live server

Isolation

A fresh container per command

  • gVisor user-space kernel (required on the server)
  • No network by default · 256 MB RAM, no swap · 1 CPU · 64 processes
  • No Linux capabilities · non-root · read-only system files
  • Per-command timeout; memory kills reported back
  • 512 MB disk quota per workspace, enforced by the kernel
API

Six endpoints, per-tenant keys

  • Create session · write · read · exec · delete · health
  • Each key belongs to a tenant; tenants can't see each other's sessions
  • Image allowlist; path and symlink escapes refused
  • Python client with the same interface as a local workspace
Egress gateway

Internet only where approved

  • Per-tenant allowlist; sessions opt in, e.g. egress=["pypi"]
  • Each session on its own private network; the proxy is the only way out
  • HTTPS to port 443 only; private and cloud-metadata addresses refused
  • Every connection logged: session, host, decision, bytes
Agent + evals

Proof that agents can use it

  • Tool-calling agent: read, write, run until tests pass
  • Model-agnostic in design; the demo uses gpt-4o-mini
  • Eval harness with hidden tests and an exfiltration task
Deployment

One terraform apply

  • EC2 in your account, HTTPS via Caddy, no SSH
  • Keys generated into SSM; IAM limited to two resources
  • Code shipped from a private S3 bundle; encrypted disk, IMDSv2
Who it's for

Builders of agents — not people using them

Agent builders · startups, indie devs

Run model-written code without risking your machine

  • Any model. The sandbox doesn't care whether the code came from GPT, Claude, Llama or Qwen.
  • Small surface. Six HTTP calls, or three methods on a client. Drop it in as the "run code" tool.
  • Self-correcting loops. Stdout, stderr, exit code and memory-kill warnings go back to the model.
  • Safety you can show. The red-team demo is a ready-made answer to "what if it runs rm -rf or phones home?"
  • Flat cost. One small VM instead of per-session billing while you experiment.
Enterprises · platform and security teams

The sandbox stays inside your perimeter

  • Data residency. Code, files and outputs never leave your AWS account or region.
  • Model choice. Use a private or on-prem model; no lab's agent platform required.
  • Auditable. About 1,200 lines of Python and 450 of Terraform. Security can read all of it in an afternoon.
  • Deny by default. No network unless a tenant policy allows a host; no SSH on the host; least-privilege IAM; keys in SSM.
  • Egress audit trail. Every outbound connection a sandbox attempts — allowed or refused — is logged per tenant and session.
  • Tenant separation. Teams or customers get separate keys and cannot touch each other's sessions.

What's missing

The honest list

Long-running sessionsEach command gets a new container. Servers, background jobs and installed packages don't survive between calls; competitors keep a live machine per agent.
Human approval for new hostsThe egress allowlist is set by policy; there's no "ask a person" step like Muse's Sentinel for hosts outside it yet.
Browser and computer useNo headless browser or desktop, which Dots, Grok Bot and Muse rely on.
Packaged SDKsA Python client exists in the repo; it isn't on PyPI, and there's no JavaScript SDK.
Command audit trailOutbound connections are logged, but not which commands ran and what they returned — the next thing an enterprise security review asks for.
Scale and per-tenant limitsOne host (100 concurrent sessions), in-memory sessions, no per-tenant caps or rate limits. Disk is quota-limited per workspace. Fine for a pilot, not for many customers.
Snapshots and templatesTwo allowed images; no way to save a prepared environment and start new sessions from it.
Where to take it

The wedge: "Sentinel for everyone else"

Meta built an approval gate for Muse's internet access because exfiltration is the risk that worries people most. Companies building their own agents want the same control, with logs they own. The egress gateway is now built; the rest of the list turns it into that product:

Built

Egress gateway

Per-tenant allowlist with every outbound connection logged. Next: human approval for hosts outside the list.

Command audit log

Every command and file write per tenant alongside the egress log, exportable for compliance.

Persistent sessions

A container that lives for the session, so agents can install packages and run servers.

SDK on PyPI

pip install, plus drop-in tool definitions for OpenAI, Anthropic and open-model agent frameworks.

Demo script · about 5 minutes

How to show it

Set the connection once (keys from terraform output -raw fetch_api_keys_command), then run the demo. In PowerShell:

$env:SANDBOX_API_URL = "https://<server-ip>"
$env:SANDBOX_API_KEY = "<key>"
$env:SANDBOX_API_INSECURE = "1"     # only without a domain (self-signed certificate)
python demo_live.py                  # or --skip-agent to avoid OpenAI calls
  1. Act 1~30 s

    Hello sandbox

    Creates a session, writes a Python file, runs it on the server and prints the output and round-trip time.

    "This code didn't run on my laptop. It ran in a throwaway container on our server, as a non-root user, and the container is already gone."

  2. Act 2~90 s

    Agent at work

    Plants three bugs in a Fibonacci function. The agent reads the files, rewrites the function, runs the tests, and stops when they pass. The demo re-runs the tests itself instead of trusting the agent's word.

    "The model only decides what to do. Every file it touched and every command it ran happened inside the sandbox. Swap in Claude or Llama and nothing else changes."

  3. Act 3~90 s

    Red team

    Runs 12 real attacks: exfiltration, stealing the server's AWS credentials, memory and fork bombs, filling the disk, an infinite loop, tampering with system files, hunting for secrets, probing the kernel, path traversal, a symlink escape, and a guessed key. Each row names the control that stopped it.

    "This is the question every security team asks: what happens when the model does something stupid, or someone tricks it into something malicious? Here's the answer, run live."

  4. Act 4~60 s

    Egress gateway

    A session allowed only PyPI installs requests, then fails to reach example.com, fails to reach the cloud metadata service, and finds no route when it bypasses the proxy. Ends on the session's egress log.

    "Agents need packages, so we don't pretend they can live offline. They get exactly the sites your policy allows, and you get a record of every connection they tried."

Act 4 needs pypi in the tenant's egress policy (Terraform: -var 'egress_policy={default=["pypi"]}').

If asked about the fork bomb: under gVisor the 256 MB memory limit ends the sandbox after roughly 10–20 processes; the server and other sessions keep running.
